# 11. 제품 검증과 계측 설계

버전 0.1 / 제품 가설 검증 계획. 임상 연구나 치료 효과 평가가 아니다.

## 1. 검증할 질문

사용자가 오늘 안 할 일을 덜어내는 방식이 우선순위를 모두 입력하는 방식보다 덜 부담스러운가. 특정 날짜에 보낸 일을 그 전까지 다시 보지 않아도 된다고 믿는가. 정리 결과의 Today가 본인의 오늘 의도와 일치하는가. 정리를 잘했는데 실제 실행은 더 어려워지는 부작용이 없는가.

기능 클릭률만으로 답하지 않는다. 많이 미루거나 앱에 오래 머문다는 것이 성공은 아니다.

## 2. 제품 가설

| ID | 가설 | 관찰 / 반증 조건 |
|---|---|---|
| H-01 | 제목만 넣으면 입력 중단이 줄어든다 | 분류를 요구하지 않아도 작업을 다시 찾지 못하면 부분 실패 |
| H-02 | 미래 확정 항목을 다시 묻지 않으면 관리 부담이 줄어든다 | 숨겨져 불안해서 전체 목록을 반복 확인하면 재등장 신뢰 실패 |
| H-03 | 오늘에 남길지를 묻는 방식이 결정을 단순하게 한다 | 과제 의미를 이해하지 못해 아무 날짜나 고르면 실패 |
| H-04 | 주만 정하기가 주간 정리 비용을 줄인다 | 월요일 확정으로 오해하거나 날짜 미정이 계속 누적되면 수정 |
| H-05 | 정리 후 Today 위젯 전환이 실행으로 이어진다 | 위젯이 계속 정리 모드여서 재배치만 반복되면 실패 |
| H-06 | 중간 종료를 허용하면 복귀가 쉬워진다 | 미검토가 Today로 오해되거나 사라졌다고 느끼면 실패 |
| H-07 | 앱 밖의 결정이 더 편하다 | 위젯 지연 / 실수로 앱보다 오래 걸리면 위젯 범위 재검토 |

## 3. 초기 사용자 검증

권고 첫 단계는 5~8명의 정성 사용성 테스트다. 할 일 기록을 잘 못 하는 사람, 목록은 쓰지만 실행이 어려운 사람, ADHD를 스스로 공개하고 참여하는 사람 등을 포함할 수 있으나 진단을 추정하거나 필수로 수집하지 않는다.

주요 과제는 20~30개 작업을 넣고 일부를 다음 주로 보내기, 특정 금요일을 선택하기, 주만 선택하기, 3분 전에 그만두기, 다음 날 돌아오기, 마감이 있는 일을 마감 이후로 보내기, 잘못 누른 항목 되돌리기다.

그 다음 실제 사용에서 1~2주 관찰한다. 이는 일정 약속이 아니라 실험 설계 제안이다. 작은 표본으로 인과적 생산성 개선이나 ADHD 효과를 주장하지 않는다.

## 4. 지표 정의

| 지표 | 정확한 의미 | 해석 주의 |
|---|---|---|
| 입력 완료율 | 입력 흐름을 시작하고 유효 작업을 저장한 비율 | 앱 / 공유 / Siri를 분리 |
| 정리 능동 시간 | 앱이 정리 화면 전경에서 실제 사용 중인 시간 | 위젯 전체 사용 시간을 직접 알 수 있다고 가정 금지 |
| 결정당 시간 | 확인 가능한 결정 구간의 소요 | 사용자 숙고와 시스템 지연 분리 |
| 재결정 노출률 | 미래 확정 항목이 이른 시점의 자동 큐에 나온 건수 | 정책 위반은 0이 목표 |
| 의도 불일치 | 사용자 설명과 실제 저장 목적지가 다른 사례 | 설문 / 관찰과 결합 |
| Today 오염 | 미검토 / 과거 미완료가 자동 Today에 들어온 건수 | 0이 필수 |
| 되돌리기율 | 완료된 결정 중 Undo 비율 | 실수와 탐색을 구분. 무조건 낮을수록 좋지 않음 |
| 마감 누락 경험 | 마감 표시 / 알림을 잘못 이해해 놓친 보고 사례 | 알림 권한 / 동기화 상태 함께 기록 |
| 재등장 신뢰 | 미룬 일을 다시 확인하지 않아도 된다는 자기보고 | 단순 리텐션과 다름 |
| 관리 후 행동 | 사용자가 선택한 일을 실제로 시작했다고 보고한 비율 | R1은 타이머 / 감시로 자동 측정하지 않음 |

3분 이하 비율의 분모는 모든 작업이 아니라 “당일 정리 시간을 기록할 수 있었던 일간 주기”다. 0초에 종료하고 아무 결정도 하지 않은 사례는 별도로 보고한다. 타이머를 강제로 닫아 지표를 좋게 만들지 않는다.

## 5. 위젯 계측 한계

앱은 위젯이 화면에 표시된 전체 시간이나 사용자가 생각한 시간을 정확히 알 수 없다. 인텐트의 시작 / 끝 시각은 처리 시간을 알려주지만 정리의 전체 능동 시간을 뜻하지 않는다.

따라서 위젯의 3분 검증은 초기에는 사용자 동의를 받은 관찰, 화면 녹화, 과제 시작 / 종료 자기보고를 활용한다. 첫 탭과 마지막 탭의 차이를 사용할 때는 `observedInteractionSpan`이라는 별도 근사치로 표시하고 능동 시간과 합산하지 않는다.

## 6. 로컬 이벤트 설계

| 이벤트 | 허용 속성 | 금지 속성 |
|---|---|---|
| capture_attempt / capture_saved | surface, 성공 여부, 길이 구간 | 제목 / 원문 |
| review_opened / review_closed | 모드, 대상 수 구간, 종료 사유 | 전체 작업 목록 |
| decision_committed | 목적지 종류, 탭 경로, 시스템 처리 시간 | 구체적 작업 제목 / 실제 마감 |
| decision_rejected | 오류 코드, surface | 원문 payload |
| undo_requested / undo_result | 성공 / 충돌 / 범위 | 원래 제목 |
| calendar_permission_changed | 권한 상태 | 캘린더 제목 / 이벤트 원문 |
| sync_state_changed | 상태, 오류 분류 | iCloud 사용자 ID |
| widget_interaction_finished | 처리 시간, 결과 | 지속적 기기 식별자 |

분석용 taskID를 외부로 전송하지 않는다. 기능용 OperationRecord와 진단 이벤트는 다르다. 기능 기록을 사용자 연구 데이터처럼 자동 수집하지 않는다.

기본은 로컬만 보관하고, 사용자 연구 참여 시 요약 데이터 export를 별도로 동의받는다. 이벤트 보존은 진단용 14일을 초기 제안으로 두되 사용자가 지울 수 있다. 작업 원본 이력의 보존과 같은 정책으로 취급하지 않는다.

## 7. 출시 전 판단 기준

데이터가 사라짐, 다른 작업이 변경됨, 미검토 Today 유입, 실제 마감 변경, 계정 데이터 섞임은 빈도와 무관하게 차단 결함이다.

작업 20개를 3분 안에 모두 처리해야 한다는 기준은 두지 않는다. 대신 일반적인 5~15개 검토 구간에서 사용자가 결정한 결과를 이해하고, 도중에 멈춰도 안전하며, 익숙해진 뒤 관리 시간이 과도하지 않은지를 확인한다. 수치는 검증 과제의 권고 범위이며 효과가 입증된 기준이 아니다.

## 8. 실패 시 수정 순서

먼저 문구와 목적지 의미를 고친다. 다음은 큐의 반복 노출, 뒤로 가기 / Undo, 주 단위 상태다. 그 다음 위젯의 패널 전환을 단순화한다. AI 자동 추천, 보상, 추가 알림은 핵심 의미와 신뢰 문제를 해결한 뒤에 검토한다.
