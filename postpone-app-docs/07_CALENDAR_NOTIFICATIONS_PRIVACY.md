# 07. 캘린더, 알림, 권한과 개인정보

버전 0.1 / 관련: [아키텍처](05_ARCHITECTURE_AND_SYNC.md), [공식 근거](10_SOURCES_AND_COMPATIBILITY.md)

## 1. 캘린더 통합 범위

R1 캘린더 기능은 기존 약속을 날짜 선택의 맥락으로 보여주는 것이다. 기존 이벤트를 수정하거나 할 일 배치를 자동으로 캘린더 이벤트로 내보내지 않는다. “화요일에 할 일”은 시간 없는 작업이고 “화요일 14시 회의”는 외부 약속이다.

EventKit은 읽기 전용 권한을 제공하지 않는다. 읽으려면 full access를 요청해야 하므로, 제품이 읽기만 한다는 정책과 OS 권한 범위를 구분해 설명한다. 근거 A10.

권한 설명 제안:

> 날짜를 고를 때 기존 약속을 함께 보여드리기 위해 캘린더 접근이 필요합니다. 이 버전에서는 약속을 변경하거나 삭제하지 않습니다.

### 1.1 EventKit adapter

| 항목 | 명세 |
|---|---|
| 소유 | 프로세스별 CalendarService가 EKEventStore 수명 관리 |
| 권한 요청 | 사용자가 “기존 약속 함께 보기”를 눌렀을 때 |
| iOS 설정 | NSCalendarsFullAccessUsageDescription 포함 |
| macOS 설정 | sandbox calendar entitlement와 해당 SDK의 사용 설명 구성 확인 |
| 조회 | 화면의 날짜 범위 + 필요한 작은 여유 범위 |
| 캐시 | 기기 로컬만. 기본 유효기간 15분을 제안하며 실제 변경 알림 시 무효화 |
| 갱신 | 앱 전경 진입, 선택 캘린더 변경, EventKit store 변경 |
| 차단 | 캘린더 쓰기 API는 R1 command layer에 노출하지 않음 |
| 미리 알림 | 접근 요청하지 않음. 양방향 연결은 후속 ADR |

캘린더 캐시 TTL은 제품 권고값이지 EventKit이 갱신을 보장하는 시간은 아니다. 오래된 캐시에는 기준 시점을 기록한다. 위젯 날짜 패널은 캘린더 캐시 실패 때문에 작업 배치를 막지 않는다.

### 1.2 표시 규칙

종일 일정은 시간 점유 합산에서 별도로 분리한다. 겹치는 두 약속의 시간을 단순 합산해 하루 가능 시간을 빼지 않는다. R1에서는 “이 날 약속 2개” 같은 사실 표시를 우선하고 자동 가용 시간 / 업무량 계산은 하지 않는다.

외부 이벤트 ID는 기기 간 동일하다고 전제하지 않는다. R1은 외부 이벤트 ID를 작업의 영구 관계 키로 사용하지 않고 기기별 조회 캐시에만 둔다. 선택 캘린더도 기기별 권한과 실제 캘린더 매핑을 재확인한다.

거절 / 제한 / 철회 시 캐시를 지우고 이후 접근을 중단한다. 캘린더가 비어 있음과 권한이 없음은 다른 empty state다.

## 2. 알림 역할

| 유형 | 목적 | 기본값 |
|---|---|---|
| 정리 알림 | 오늘 또는 이번 주를 짧게 정하도록 제안 | 사용자 선택 후 활성화 |
| 실제 마감 알림 | 명시적으로 설정한 실제 시한 안내 | 해당 작업에서 사용자 설정 |
| 배치 날짜 알림 | 모든 배치일마다 추가 알림 | R1 기본 비활성. Today / 정리로 재등장 |
| 동기화 문제 | 저장 상태 설명 | 지속 오류일 때 앱 내부. 반복 푸시 금지 |

마감 알림과 정리 알림은 서로 다른 채널 의미를 가진다. 하루의 모든 작업을 같은 소리로 반복 재촉하지 않는다. Critical Alerts와 Time Sensitive를 기본값으로 요구하지 않는다.

로컬 알림의 예약 / 취소는 UserNotifications를 사용한다. 실제 전달 시각은 시스템 알림 설정, 집중 모드, 기기 상태의 영향을 받으므로 사용자가 원하는 모든 상황에서 정확한 시각에 표시된다고 보장하지 않는다. API 근거 A16.

## 3. 정리 알림 예약 정책

권고 기본 시각은 09:00이며 첫 설정에서 바꿀 수 있다. 주간 정리는 월요일이 기본이다. 이 수치는 사용자에게 확정받은 값이 아니라 시작 가능한 권고값이다.

정리 알림은 향후 28개 계획 날짜의 비반복 request를 예약하는 방식을 제안한다. 각 날짜에 일간 또는 주간 알림 하나만 둔다. 주간 날짜에는 일간 알림을 추가하지 않는다. 알림 request ID는 `review:<workspaceEpoch>:<planningDate>`로 안정적으로 만든다.

해당 날짜의 기본 정리를 알림 시각 전에 마쳤다면 당일 pending request를 제거한다. 앱 / 인텐트 실행 시 다음 예약 범위를 보충한다. 28일보다 오래 앱이 전혀 실행되지 않으면 예약이 끝날 수 있으므로 무기한 알림 보장을 하지 않는다. 이 제약이 실제로 문제가 되면 후속에서 반복 알림과 완료 억제의 trade-off를 재검토한다.

예약량 28은 제품 정책이다. OS의 최대 예약 개수라고 주장하지 않는다. 마감 알림을 포함한 자체 총량 상한은 48개를 제안하고 실제 API 오류를 확인한다. 한도를 넘으면 가까운 명시 마감과 가까운 정리 날짜를 우선하되 누락된 예약 수를 진단 화면에 표시한다. 먼 마감 데이터 자체를 삭제하지 않는다.

## 4. 마감 알림 정책

실제 마감을 설정하는 것과 알림을 허용하는 것은 별개다. 사용자가 선택한 시각을 NotificationPreference에 저장한다. 날짜만 있는 마감은 별도 시각을 선택하며 시간을 임의로 만들어 deadline 데이터에 섞지 않는다.

작업 완료 / 휴지통 / 마감 제거 시 pending 및 관련 delivered request를 정리한다. 계획만 내일로 바꾼 경우 마감 알림은 유지한다. 알림 시각이 이미 지난 데이터를 가져오면 즉시 과거 알림 수십 개를 발송하지 않고 앱의 마감 안내에 표시한다.

### 4.1 다중 기기

알림은 기기별로 전달되므로 R1은 첫 iPhone을 기본 알림 기기로 제안하고 Mac / iPad는 사용자가 추가 활성화하게 한다. 앱이 다른 모든 기기의 pending request를 즉시 취소할 수 있다고 가정하지 않는다.

Mac에서 완료한 직후 iPhone이 오프라인이면 기존 알림이 남을 수 있다. iPhone이 변경을 수신하면 취소한다. 이런 경계에서 “알림 절대 중복 없음”을 약속하지 않는다. 사용성 문구는 “이 기기에서 알림 받기”처럼 정확하게 한다.

## 5. 권한 행렬

| 기능 | 권한 / 동의 | 요청 시점 | 거절 시 대체 |
|---|---|---|---|
| 기본 작업 입력 / 정리 | 없음 | 없음 | 항상 가능 |
| 캘린더 읽기 | EventKit full access | 기존 약속 보기 선택 | 할 일 날짜만 표시 |
| 정리 / 마감 알림 | UserNotifications | 알림 설정 선택 | 앱과 위젯에서 확인 |
| iCloud 동기화 | OS 계정과 동기화 활성화 선택 | 다른 기기에서 사용 선택 | 로컬 전용 |
| 음성 텍스트 | 시스템 받아쓰기 / 사용자가 만든 단축어 | 해당 시스템 흐름 | 키보드 입력 |
| 사진 / 마이크 / 위치 | R1 요청 없음 | 없음 | 공유한 텍스트 / URL만 수용 |
| 시스템 검색 노출 | 앱 내 사용자 선택 | Spotlight 기능 안내 | 앱 내부 검색 |

권한 요청은 핵심 흐름을 막는 첫 화면의 체크리스트가 아니다. 재요청이 불가능한 상태에서는 설명과 설정 이동을 제공하되 매 실행마다 강요하지 않는다.

## 6. 민감 정보와 위젯

할 일 제목에는 진료, 관계, 금융 같은 내용이 들어갈 수 있다. 개인정보를 직접 분석하거나 진단하지 않고 모든 자유 입력을 민감할 수 있는 데이터로 취급한다.

위젯의 표시와 명령 실행은 다른 보안 문제다. 제목 가리기는 이미 렌더링된 화면 노출을 줄이는 기능이고 authenticationPolicy는 실행 허용 범위를 정한다. 하나가 다른 하나를 대체하지 않는다. A14.

권고 정책:

| 상태 | 표시 / 동작 |
|---|---|
| 사용자가 위젯 제목 표시 허용 | 최소 제목과 날짜만 표시. 긴 메모 / URL 숨김 |
| 앱 전체 외부 제목 숨기기 | “할 일 1개”, 날짜, 앱 열기 |
| 잠금 / 보호 데이터 접근 불가 | 안전한 자리표시자. 보호 완화 없이 인증 / 앱 경로 |
| Spotlight 노출 꺼짐 | 기존 인덱스 제거. 시스템 질의 반환 범위 제한 |
| 로그 / 오류 | 작업 제목과 메모 없이 오류 코드, 단계, 건수 |

system snapshot과 이미 전달된 알림까지 순간적으로 완전히 회수한다고 보장하지 않는다. 개인정보 설명에서 이 한계를 숨기지 않는다. 파일 보호 수준은 실기기 잠금 테스트를 통과한 뒤 정하고, 배경 편의를 위해 데이터 보호를 무작정 낮추지 않는다.

## 7. 데이터 흐름과 수집

| 데이터 | 저장 위치 | 외부 전송 |
|---|---|---|
| 작업 / 계획 / 마감 / 변경 이력 | 로컬 원본과 투영 | iCloud 활성화 시 Apple private database |
| 캘린더 원문 | EventKit, 짧은 로컬 캐시 | 자체 서버와 CloudKit에 재업로드하지 않음 |
| 정리 세션과 위젯 패널 | 기기 로컬 | 기기 외부로 보내지 않음 |
| 진단 | 민감 값 없는 로컬 로그 | 사용자 명시 공유 시에만 |
| 사용성 계측 | 기기 로컬, 동의 시 연구용 요약 | 기본 외부 전송 없음 |
| URL | 사용자 원문 | 사용자가 열 때 해당 사이트에 접근 |

CloudKit private database를 쓴다는 이유만으로 모든 필드가 무조건 종단간 암호화된다고 광고하지 않는다. 시스템 계정과 백업 설정에 따른 보호를 별도로 검토해야 한다. R1은 “로컬 우선, 선택적 iCloud 동기화, 자체 분석 서버 없음” 정도의 확인 가능한 설명을 사용한다.

자유 입력을 시스템 단축어의 다른 동작이나 외부 모델에 전달하는 것은 사용자가 구성한 별도 흐름일 수 있다. 앱이 직접 서버 AI를 쓰지 않는 것과 모든 사용자 단축어가 오프라인이라는 주장은 다르다.

## 8. 링크와 입력 보안

공유 / 붙여넣기 텍스트를 코드나 명령으로 실행하지 않는다. R1에서 외부 URL 미리보기 자동 수집은 하지 않는다. URL을 열 때 스킴을 검증하고 `javascript:`, 임의 파일 접근, 앱 내부 mutation URL을 입력 콘텐츠가 실행하게 하지 않는다.

자체 딥링크는 탐색만 수행한다. taskID를 알았다는 이유로 다른 계정 데이터를 읽거나 변경할 수 없게 현재 저장소 범위를 검증한다. 길이 초과, 잘못된 인코딩, 존재하지 않는 ID는 안전한 오류로 처리한다.

## 9. 내보내기와 복원

export에는 작업 제목과 변경 이력이 들어간다는 경고를 제공한다. 파일은 사용자가 선택한 위치에 생성한다. 기본적으로 평문 JSON이므로 암호화된 백업이라고 표현하지 않는다. 공유가 끝난 임시 파일은 가능한 범위에서 정리한다.

restore는 전체 파일을 검사한 뒤 미리 보기에서 새 작업 / 중복 / 손상 건수를 표시한다. 알 수 없는 버전, 같은 ID 다른 payload, 계정이 다른 자료는 자동 병합하지 않는다. 원본 이력에서 개인 정보가 복원될 수 있다는 점을 설명한다.

## 10. 휴지통과 영구 삭제

휴지통은 즉시 실행 가능한 복구 가능한 기능이다. R1 권고는 휴지통 자동 비우기를 하지 않는 것이다. 개별 작업의 이력이 불변 로그에 있으므로 projection 하나만 지우고 “영구 삭제”라고 부르지 않는다.

R1에서 **개별 작업의 이력까지 선택 삭제하는 기능은 후속 범위**로 둔다. 대신 현재 기기 데이터 삭제와 개인 공간 전체 삭제의 차이를 분리한다. 공개 출시 전에는 전체 삭제 흐름의 G-DELETE를 통과해야 한다.

### 10.1 이 기기에서만 지우기

동기화 연결을 중지하고 로컬 원본 / 투영 / 위젯 snapshot / 인덱스 / 알림을 제거한다. CloudKit 자료를 삭제한 것으로 표시하지 않는다. 다시 동기화하면 자료가 다시 내려올 수 있음을 설명한다.

### 10.2 iCloud 포함 개인 공간 전체 삭제

인터넷 연결과 명시적 이중 확인이 필요하다. export를 먼저 선택할 수 있으나 강제하지 않는다. 쓰기와 위젯 mutation을 막고, 해당 공간의 원본 CloudKit zone 및 대응 로컬 원본을 삭제한 뒤 캐시와 인덱스 / 알림을 정리한다. Core Data에는 zone record와 대응 managed object를 purge하는 API가 있으나 실제 Swift 서명과 사용 중 zone ID는 SDK에서 확인한다. 근거 A19.

다른 오프라인 기기의 캐시까지 즉시 삭제할 수는 없다. 기기별 삭제 확인과 `workspaceEpoch` 변경을 통해 구세대 데이터가 새 공간에 재수입되지 않도록 해야 한다. 자동 미러링이 다시 온라인이 되는 순서와 purge 후 복구 동작은 공개 문서만으로 해결된 것으로 간주하지 않는다.

G-DELETE 실험에서는 오래 오프라인인 두 번째 기기를 다시 연결해 원본이 재업로드되거나 현재 공간에 부활하는지 확인한다. 이 실험을 통과하기 전에는 “모든 기기에서 완전히 삭제됨”이라고 안내하지 않는다. 제한이 남으면 삭제 대상 기기 목록과 추가 조치를 정확히 표시하고 공개 출시를 보류한다.

## 11. 공개 배포 전 개인정보 문서

PrivacyInfo.xcprivacy, 실제 사용하는 required-reason API, 포함한 SDK, 앱 개인정보 표시를 빌드의 실제 데이터 흐름과 일치시킨다. 이 문서가 “수집 없음”을 선언해 준다고 생각하지 않는다. 공식 공개 지침은 A18을 확인한다.

자체 분석 SDK를 넣는다면 수집 이벤트, 전송 대상, 보존 기간, 동의와 해제, 삭제 방법을 추가 ADR로 승인해야 한다. ADHD 관련 정보나 건강 상태를 온보딩에서 불필요하게 수집하지 않는다.
