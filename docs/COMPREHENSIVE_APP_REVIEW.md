비교 기준 `95146d2`의 [기본 배포 검사 105](https://github.com/hellosunghyun/mirror/actions/runs/37171133307)는 SwiftPM과 세 플랫폼 앱·확장 빌드 및 단위 단계는 성공했지만 실제 UI 단계는 모두 실패했다. iPad는 일부 사례가 통과했고 전체 수용은 아니다. IPA·DMG 생성과 게시 단계는 건너뛰었다. 새 변경의 성공 근거로 이 이전 실행을 사용하지 않는다.

실패 로그와 이미지는 실행 SHA·attempt 및 artifact digest를 확인한 뒤 읽는다. XCTest query와 상세 이력 탐색의 알려진 오류만 고정 enum으로 요약한다. 원문 AX·제목·경로·값을 공개 공지로 전송하지 않으며 진단 정보는 통과 판정·assertion·시간 제한을 바꾸지 않는다. 추가 audit 콜백도 `.all`을 유지하고 항상 `false`를 반환해 어떤 issue도 무시하지 않는다.

`ecebd93`의 [Adaptive 실행](https://github.com/hellosunghyun/mirror/actions/runs/37193375345)에서 Mac system 앱과 runner 빌드는 성공했지만 네 사례가 첫 접근성 감사 호출에서, 계획 입력 사례가 추가 옵션 펼침 뒤 `capture.planToday`의 존재·고유성 검사에서 실패했다. 이후 복구한 실제 로그에서 입력 감사의 `Parent/Child mismatch`, 정리·검색·좁은 창 감사의 `Element has no description`을 확인했다. 구체적인 대상 요소는 아직 확정하지 않았으며 지원 불가나 앱 중단으로 단정하지 않는다. 전체 헤더 버튼은 조작 개선이며 실패 원인 확정이나 수용 통과를 뜻하지 않는다.

같은 실행의 Mac 실패 화면 4장과 iPhone dark 정리 화면 1장을 직접 확인했다. 정리를 시작한 화면에 이전 입력 안내와 Undo가 남고, 최대 글자 요청에도 정리 버튼이 일반 크기의 가로 배치를 사용하는 문제가 관측됐다. 루트 환경 검사만으로 별도 창의 최대 글자 수용을 보장할 수 없어 세션 표시와 창별 환경 전달·검사를 보강한다. 이 사진은 `ecebd93`의 실패 진단이며 후속 소스나 전체 흐름의 시각 수용은 아니다. iPad 화면은 아직 직접 확인하지 못했다.

동일 소스의 [기본 실행 106](https://github.com/hellosunghyun/mirror/actions/runs/37193375591)에서는 SwiftPM 240개 실행 중 위젯 동시 결정 사례가 `busy`로 실패했다. 앞선 전부 통과 기록으로 이 재현을 덮지 않는다. 같은 프로세스의 두 요청이 전체 저장·표시 갱신 잠금 안에서 250ms 안에 끝나야 하던 경쟁을 수정하고 기존 동시 결정 회귀의 기대값·시간 제한을 유지한다.

`ecebd93` 기본 실행 106의 Mac 결과 artifact를 SHA-256으로 검증하고 실제 ui.log를 읽었다. 확인한 다섯 실패 기록 중 세 건은 설정·입력 창을 연 뒤 `Timed out while evaluating UI query.`, 두 건은 새 사례의 초기 `today.list` 조회에서 대상 프로세스 main-thread busy였다. 모달 사례는 닫기 조회 전에 idle 대기부터 길어져 버튼 ID만의 문제로 판단할 수 없다. 독립된 crash·hang·sample 스택 파일은 없으며 XCResult 내부 진단 첨부는 실제 SDK로 확인해야 한다. 상태 갱신·로컬 projection 알림·배치의 정적 검토만으로 무한 반복을 입증하지 못했으므로, 이를 원인으로 가정해 조회 방식이나 검사 시간을 바꾸지 않는다.

[보존 결과 진단 workflow](../.github/workflows/mac-ui-hang-diagnostics.yml)는 이 완료된 Mac job과 artifact·실행·소스·UI bundle digest를 고정해 확인하고 Xcode 27의 공개 export 옵션을 검사한다. 새 앱 실행 없이 보존된 XCResult의 diagnostics·attachments를 내보내며 공개 결과에는 종료 상태와 확장자별 개수만 담는다. 첨부 내용·스택 해석이나 UI 수용 성공을 뜻하지 않는다. 기존 실패 요약에는 확인된 두 SDK 메시지에만 `uiQueryEvaluationTimeout` 또는 `processMainThreadBusy` 분류를 추가하며 원문·사용자 데이터·검사 기준은 그대로 보호한다. 실제 진단 workflow 결과는 아직 대기 중이다.

`e1bb1f3`의 전체 추가 입력 헤더 변경 뒤에도 Mac의 계획 입력 조회 실패가 재현됐다. Adaptive 진단은 소스·테스트 소유권과 실패 종료를 확인한 경우에만 `missing` 또는 `nonUnique` 고정 값으로 존재 확인과 개수 검사 실패를 구분한다. 개수 검사 실패는 조회 시점의 `count != 1`을 뜻하며 화면 중복으로 단정하지 않는다. 원문 UI 데이터, 검사 시간 제한과 통과 기준은 바꾸지 않는다.

`6cb236d` Mac Adaptive에서는 계획 입력의 `capture.planToday` 존재 확인이 `missing`으로 실패했다. 날짜 선택 영역은 자식 버튼을 유지하는 이름 있는 접근성 그룹으로 명시하고, 펼친 그룹과 그 안의 고유한 오늘 버튼을 확인한 뒤 기존 동작을 수행한다. identifier 상속이나 펼침 실패 중 무엇이 원인인지는 아직 확정하지 않는다. Batch 취소 검사는 스크롤 밖의 iOS 상단 헤더·Mac toolbar와 일치하도록 기존 실제 창 기준을 사용하며 고유성·전체 표시·조작 가능 여부·iOS 44pt와 도메인 assertions를 유지한다. 이 화면 계약 수정은 관측한 Phone scroll owner 실패의 원인 확정을 뜻하지 않는다.

`748672d`의 [Batch 실행](https://github.com/hellosunghyun/mirror/actions/runs/37197743914)에서도 Mac은 빌드 뒤 두 사례가 초기 `capture.close` snapshot 조회에서 실패했다. iPhone은 UI 단계가 1,213초 뒤 기존 20분 제한으로 중단됐다. 정확한 iPhone 조작 위치는 미상이다. 이 workflow는 XCTest 원문을 별도 파일에 기록하므로 GitHub job log에 사례 활동이 없었고, 중단 시 native 종료 상태를 아직 받지 못한 EXIT trap은 기존 고정 진단을 호출하지 않았다. 검사 시간이나 성공 기준을 바꾸는 대신, 이런 중단에서도 현재 사례의 마지막 고정 진행 단계를 확인하도록 진단을 보완한다. 진행 정보는 부분 관측이며 실제 두 사례의 typed 성공 결과를 대신하지 않는다.

`748672d`의 같은 [Adaptive 실행](https://github.com/hellosunghyun/mirror/actions/runs/37197743932)에서 iPad system은 빌드 성공 뒤 UI 단계가 1,213초에 중단됐다. 실제 SDK 로그는 입력 저장 버튼의 `Dynamic Type font sizes are unsupported`, 링크 안내·정리 날짜 설명·상단 추가 버튼의 `Contrast failed`를 보고했다. 두 설명 문구는 기존의 더 선명한 `MirrorPalette.supportingText`를 적용한다. 상단 버튼은 측정된 색상이나 화면이 없어 원인을 확정하지 않는다. 최대 크기를 SwiftUI 환경에 고정한 테스트와 시스템 설정에 따른 Dynamic Type 지원 검사는 별도로 원인 분리가 필요하며 저장 버튼의 고정 글꼴 문제로 단정하지 않는다. 전체 감사와 실패 기준은 유지한다. 같은 iPad 실행에서 펼친 날짜 그룹과 고유한 오늘 버튼의 조회·선택, 저장 버튼 문구 변경까지 확인했지만 계획 저장은 감사 이후 단계이므로 통과로 기록하지 않는다. 최신 화면 이미지와 수정 뒤 대비 검사는 아직 미확인이다.

## 전체 완료까지 남는 구현과 검증

- App Group·iCloud Container의 실제 Apple 등록과 서명 entitlement 연결이 필요하다. 현재 빈 설정을 임시 경로의 성공으로 대체하지 않는다. 위젯·공유 확장·실제 두 기기 동기화의 수용을 유지한다.
- 개인 공간 전체 Cloud 삭제의 authority/purge와 오래된 writer·importer의 부활 차단은 아직 완료되지 않았다. 로컬 삭제나 지원 상태 확인을 전체 삭제로 표시하지 않는다.
- 날짜·목록·단일 작업의 전용 읽기와 앱의 중복 정렬 제거를 구현했다. 반복 snapshot의 원본 정렬은 actor 내부 메모리에 재사용하고 모든 원본 쓰기에서 무효화한다. 첫 조회와 변경 뒤 첫 조회는 원래 전체 정렬을 수행하며 배열 buffer 하나를 추가로 보유한다. Today·위젯은 실제 기록의 순서 계약을 유지한다. 대량 데이터 cold open·paging·Spotlight의 안전한 증분 갱신과 새 source의 정량 성능·메모리 검증은 보완 대상이다. 10000개 작업·100000개 기록의 SQLite 측정, 명령·archive 왕복과 실제 기기 Q-086을 구분한다.
- 편집자는 한 명만 등록하고 중앙 선택 변경을 보호한다. 변경 없는 자기 편집은 요청 경로로 즉시 전환·닫고, 수정된 초안은 확인 뒤 자기 등록만 해제한다. 저장 실패·pending은 원문을 유지하며 오래된 저장 응답이나 다른 창의 닫기는 새 편집자를 해제하지 않는다. 실제 두 창·관측 재시작·원격 이벤트의 수용은 별도로 필요하다. 창별 독립 선택과 텍스트 포커스는 공유 모델의 남은 제약이다.
- 플랫폼마다 밝은/어두운 화면, 큰 글자, 좁은 창, 키보드, VoiceOver, Reduce Motion/Transparency, iPad Split View와 Mac inspector를 확인한다. UI 실패를 skip하거나 assertion·typed 수용 게이트를 줄여 통과시키지 않는다.
- 새 source의 실제 IPA·공증 DMG·GitHub Release 자산을 확인한다. 인증서 사전검사, 빌드, archive, 공증, 게시 결과를 구별한다.

모든 테스트와 앱 빌드는 사용자 지정대로 GitHub Actions 러너에서 실행한다. 원본 문서·도메인 불변식·명령/reducer·멱등성·원본 우선 저장·stale/Undo 보호를 보존하며, 검사 결과가 없는 부분은 미검증으로 남긴다. 새 오류를 근거 없이 SDK 내부 원인으로 단정하지 않는다.
